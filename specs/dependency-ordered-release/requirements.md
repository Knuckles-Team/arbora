# ARBORA-RELEASE requirements

| ID | Requirement | Verification |
|---|---|---|
| `ARBORA-RELEASE-R001` | **Dependency-ordered, digest-verified release promotion.** Arbora validates digest-pinned candidate images in a dedicated Kubernetes test namespace before promoting them, and performs its dependency-ordered pushes to each repository in sequence, checking that repository's continuous-integration result before advancing to the next. | An integration test against a fixture dependency graph confirms the rollout stops before the next stage when a predecessor's digest or CI result is missing. |
| `ARBORA-RELEASE-R001.1` | **A version tag publishes the wheel and the sdist.** The `build` job of `.github/workflows/release.yml` builds the wheel and the source distribution. Both files go into one build artifact. On a `v*` tag, the `publish` job uploads both files to PyPI. The `pypi-publish` environment has no required reviewer, so no manual approval holds the tag. A pre-release tag such as `v0.1.8.dev1` follows the same path. Its GitHub release is a pre-release, never the latest release. Deployments install the published release from PyPI only. | `tests/deployment/test_release_workflow_sources.py::test_tag_publishes_wheel_and_sdist` reads the workflow. It finds that `build` makes both files, that the artifact carries both, and that `publish` uploads both on a tag. |
| `ARBORA-RELEASE-R002` | **Local Kubernetes validation gates every push.** Arbora runs local Kubernetes validation in a dedicated test namespace as part of release qualification. The release process refuses to push or deploy until the repository's local gates report green. | A negative integration test confirms a push is blocked while a local gate is failing and proceeds once all local gates report green. |
| `ARBORA-RELEASE-R003` | **Exit-criteria matrix maps readiness to tests.** Arbora maintains an exit-criteria matrix mapping each release-readiness obligation to an executable test, including ingestion receipts, proofs over SPARQL and natural-language queries, one complete multi-agent orchestration graph, connector certification, one write-back receipt, a browser-and-identity-provider login probe, and a typed-abstention response to an agent-capability question. | A test-suite audit confirms every row of the exit-criteria matrix resolves to a passing automated test. Rollup; see `ARBORA-RELEASE-R003.1` onward (split 2026-10-09, net-new: no exit-criteria model existed). |
| `ARBORA-RELEASE-R003.1` | **Exit-criteria matrix registry and audit mechanism (arbora side, against the currently pinned epistemic-graph).** Arbora defines the exit-criteria matrix as a typed registry of obligation -> test-node-id rows and an audit function a test-suite audit runs against pytest's collected node IDs; an unregistered or uncollected obligation audits as missing, never a silent pass. | A unit test confirms the audit function marks a row satisfied when its test node ID is present among collected test IDs and missing when it is absent. |
| `ARBORA-RELEASE-R003.2` | **Full exit-criteria matrix closes green across all seven obligations.** Each of the seven obligation rows (ingestion receipts, SPARQL/natural-language query proofs, the multi-agent orchestration graph, connector certification, the write-back receipt, the browser-and-identity-provider login probe, and the typed-abstention response) is registered against a real, currently-passing cross-repo test once the epistemic-graph v2.28 release (the 44-PR integration audit it is gated on) lands, since several obligations exercise epistemic-graph capabilities this repository cannot certify against a release that has not been cut. | A test-suite audit confirms every row of the exit-criteria matrix resolves to a passing automated test. |

| `ARBORA-RELEASE-R003.4.1` | **Served task-plan run (validation checks c22 and c21).** Arbora serves one registry operation, `agents.plan_run`. The caller supplies explicit tasks (`task_id`, `prompt`, `depends_on`), an output task and limits. Arbora asks the engine for the plan through its `TaskPlan` decision (`EG-CQ-ORCH-R001`, `EG-DECISION-ENGINE-R134.111`). It uses the caller's own authenticated engine client. Arbora checks the returned receipt against the request and the verified caller principal before any task starts. It maps the engine plan one to one onto a harness `RunPlan` with a `DependencyPlan` (`AU-BOUNDARY-R043.6`). The harness runs the tasks in dependency order. At most the plan's `max_concurrency` tasks are active, and that limit is at most 8. Every task runs inside the caller's run-authority scope, so each child task inherits the caller-credential renewal. Arbora holds no planner. It never derives a plan from free text. It never adds, drops, reorders or re-validates tasks. Engine refusals such as `plan_cycle`, `missing_dependency` and `plan_bounds` pass through unchanged. A receipt mismatch refuses with `RECEIPT_MISMATCH`. An engine release without `TaskPlan` refuses with `UNAVAILABLE`. Neither refusal starts a task. Fan-out aggregation binds to `ARBORA-FLEET-R024.11`. | `tests/api/test_plan_run_ops.py` covers these cases. A five-task DAG runs every dependent after its prerequisites. The result carries the output task's result and the engine plan digest. The engine refuses a cycle and a missing dependency with its own codes, and no task starts. Arbora refuses a receipt for another principal before any task starts. Twenty independent children feed one join task. At most eight children run at a time, and the result carries every child result. |
| `ARBORA-RELEASE-R003.4.2` | **Plan attached to the work item.** A plan run can name a work-item lease (`run_id`, `worker_id`, `lease_epoch`, `fencing_token`). Arbora then publishes the engine plan and its proposal to that work item's current plan through `PublishCurrentPlan` before any task starts (`EG-DURABLE-KERNEL-R028.5.2`, `EG-DURABLE-KERNEL-R028.5.3`). The idempotency key is the run and the plan digest. Replay and recovery read the same plan. The engine checks the fence. | `tests/api/test_plan_run_ops.py::test_work_item_run_publishes_the_same_plan_for_replay` proves three facts. The published snapshot carries the plan that ran and its proposal. The request carries the lease fence and a run-and-digest idempotency key. A replay of the same proposal reads the same plan digest. |
| `ARBORA-RELEASE-R003.4.3` | **Dependency floors for served task plans.** Arbora depends on `agent-utilities>=3.1.0`, the first release with `DependencyPlan`. Arbora also depends on the first engine release that serves `TaskPlan`, `epistemic-graph[server]>=2.27.5`. Both come from the package index only. The engine floor keeps its current value until the index has that release. Until then, `agents.plan_run` refuses with `UNAVAILABLE` against the installed engine. | The lock resolves both floors from the package index. The served tests use the installed engine facade, not a fake. |
| `ARBORA-RELEASE-R003.4.4` | **Published task-plan schema pin.** The engine exports the task-plan feature schema as `TASK_PLAN_FEATURE_SCHEMA`, with its body, `schema_version` and content digest. `scripts/gen_api.py` pins that body and its content digest from the installed engine to `arbora/api/generated/task_plan_schema.json`. `gen_api.py --check` fails when the committed pin differs from the installed engine. At server start-up, Arbora compares the committed body digest with the installed export. On a match, Arbora publishes the body to the Agent Library once per tenant, starting with the process tenant. The publish is idempotent, and a current entry with the same body is reused. Arbora uses the `definition_digest` that the engine returns as the pin for `agents.plan_run`. On a mismatch or a missing export, Arbora logs the reason, and `agents.plan_run` refuses with `UNAVAILABLE`. Arbora never makes up a definition digest. | `tests/api/test_task_plan_schema_pin.py` uses a fixture export. Generation pins the body and digest, and an export that does not hash to its digest is refused. A digest mismatch or a missing export binds nothing and logs the reason. Concurrent calls publish once per tenant and return the engine definition digest. The publish request passes the engine request model, and a current entry is reused. The committed pin matches the installed engine. |

| `ARBORA-RELEASE-R003.9` | **Fleet acceptance row.** A rollout must pass the fleet acceptance check before promotion. The check runs `acceptance/acceptance.py --only fleet` from the arbora deployment stack. Each configured connector must pass four checks. Check (a): arbora reports the child healthy. Check (b): the catalog tool count equals the ledger count for the deployed version. Check (c): one read-only call succeeds through `fleet.call`. Check (d): the engine holds the current connector pack. A connector may skip only through the reasoned expected-skip list. A `GAP` result is never a pass. One `FAIL` blocks promotion. The JSON receipt names each connector, its four results and its cause. | A served test runs the fleet scenario against a two-connector fixture, with one passing connector and one stale pack. It asserts one PASS, one FAIL and a blocked promotion. |
