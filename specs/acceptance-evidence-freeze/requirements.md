# ARBORA-ACCEPTANCE requirements

| ID | Requirement | Verification |
|---|---|---|
| `ARBORA-ACCEPTANCE-R001` | **Typed acceptance-evidence model and freeze-gap checker.** Arbora ships a typed model of the three evidence kinds a requirement needs for `ACCEPTED` (`merged_head`, `test`, and operational `consumer`/`release`, all at the same commit) and a checker that, given a spec's `status.json`, lists every `LANDED`/`CLOSED` requirement missing one or more of those kinds at its `merged_head` commit. | A unit test against a fixture `status.json` asserts the checker reports exactly the gapped requirement IDs with their missing evidence kind names, and a refusal test asserts a malformed or missing `status.json` raises rather than reporting a false pass. |
| `ARBORA-ACCEPTANCE-R001.1` | **implement the typed EvidenceRecord/RequirementGap model and gaps_for_status/load_status functions plus the standalone CLI entry point in scripts/check_acceptanc.** Child slice of `ARBORA-ACCEPTANCE-R001` (see tasks.md). | A unit test against a fixture status.json asserts the checker reports exactly the gapped requirement IDs with their missing evidence kind names, and a refusal test asserts a malformed or missing status.json raises rather than reporting a false pass |
| `ARBORA-ACCEPTANCE-R002` | **Auditor distinct from delivery lane.** A requirement's `acceptance_state` moves from `NOT_AUDITED` to `ACCEPTED` only in a change where the reviewing identity differs from the author of the `merged_head` commit it cites, and only after `ARBORA-ACCEPTANCE-R001`'s checker reports no gap for that requirement. | A review-trail test over a sample `status.json` edit asserts the recorded auditor identity differs from the cited commit's author, and that the checker was run (or its report attached) before the state flip. |
| `ARBORA-ACCEPTANCE-R003` | **Evidence is append-only.** Once an evidence entry is recorded for a requirement, its `kind`, `commit`, `result`, and `url` fields are never rewritten in place; a correction is a new appended entry, and the checker only honors entries matching the requirement's current `merged_head` commit. | A regression test diffs two revisions of the same `status.json` and fails if any existing evidence entry's fields changed rather than a new entry being appended. |
| `ARBORA-ACCEPTANCE-R004` | **Operational evidence tracks the current commit, not a stale one.** A `consumer` or `release` receipt satisfies the `ACCEPTED` gate only when recorded against the requirement's current `merged_head` commit; a receipt recorded against a superseded commit is treated as missing. | A fixture test moves a requirement's `merged_head` forward without a fresh operational receipt and asserts the checker reports the operational-evidence kind as missing again. |
| `ARBORA-ACCEPTANCE-R005` | **Checker is the only path to an `ACCEPTED` report.** The acceptance-evidence checker is runnable standalone (as a script or an importable module) against any spec directory under `specs/`, producing a deterministic, machine-parseable gap report with no network or live-cluster dependency. | A CLI invocation test runs the checker against each tracked spec's `status.json` offline and asserts exit code and report shape are deterministic across two consecutive runs. |
| `ARBORA-ACCEPTANCE-R006` | **Concept-proof scenarios define done for each delivery phase (rollup).** A phase is done only when its scenario passes on `main`. Each scenario enters through the public arbora boundary and leaves a durable `ScenarioRun` record in medulla (`MEDULLA-SDLC-R013`). Each phase's release bundle completes when its rows are VERIFIED and the scenario passes (`PIPE-RELEASE-R020`). Children `.1`–`.4` and `.7` define phases P1–P5. Every family that no earlier scenario exercises is phase P5 and waits for P4. Phase P5 is done when `.7` passes. | Each child names its scenario test. The nightly scenario job (`PIPE-RELEASE-R020`) runs every scenario on `main`. |
| `ARBORA-ACCEPTANCE-R006.1` | **P1 scenario: the minimal closed loop on one node.** Steps: 1. Principal A of tenant T authenticates (`ARBORA-IDENTITY`). A calls the served `memory.remember` operation (`MEDULLA-DECISION-ENGINE-R651`). The claim commits before the acknowledgement, with actor, source, time and confidence (`MEDULLA-DURABLE-KERNEL-R078`). 2. A run for principal B of tenant T starts through `meristem.graph.execute_graph` (`MERISTEM-HARNESS-CYCLE-R001`). It retrieves through the served `RetrievalRound` (`MEDULLA-FEDERATED-QUERY-R081`), which joins a graph neighbourhood with a vector match. 3. The run injects the bounded context bundle (`MEDULLA-FEDERATED-QUERY-R650`) into its next step. 4. The run trace (`MEDULLA-ORCH-VOCAB-R009`) lists the retrieved claim IDs. 5. Principal C of tenant U retrieves nothing. 6. With the engine stopped, arbora refuses the call and no state is written. Pass: the claim returns with all provenance fields, the trace links it to the run, and steps 5 and 6 refuse with stable codes. Children: `.1` the counterfactual control, `.2` decision provenance, `.3` the phase gate. | Test: `tests/scenarios/test_p1_closed_loop.py::test_write_retrieve_under_policy_and_trace` runs arbora, a loopback medulla server and an in-process meristem run. |
| `ARBORA-ACCEPTANCE-R006.1.1` | **P1 counterfactual control: the retrieved claim changes the next action.** Behaviour: the scenario runs the same task twice on the same fixture. The test seeds the claim `deploy window is closed` for tenant T. Run A retrieves it through the `R006.1` steps 1 to 3 and injects it. Run B takes the same task without the claim, once on an empty store and once with the claim refused to B by policy (`ARBORA-IDENTITY`). The fixture model is deterministic: it returns the named action `defer_deploy` when the injected bundle holds the claim and the named action `start_deploy` otherwise. The scenario asserts that run A chose `defer_deploy`, that both B runs chose `start_deploy`, and that the two actions differ. Caller chain: the test client → served `memory.remember` and the served `RetrievalRound` over HTTP and MCP at the arbora boundary → `meristem.graph.execute_graph` (`MERISTEM-HARNESS-CYCLE-R001`) → the injected bundle (`MEDULLA-FEDERATED-QUERY-R650`) → the run step that returns the chosen action. Shape: `ScenarioRun.counterfactual { claim_id, with_claim_action, without_claim_action, refused_by_policy_action }`, each action a stable name. Refusal codes: `SCENARIO_ACTION_UNCHANGED` when the actions are equal, `SCENARIO_CONTROL_MISSING` when either control run did not execute. Depends on: `ARBORA-ACCEPTANCE-R006.1`. | Test: `tests/scenarios/test_p1_closed_loop.py::test_retrieved_claim_changes_the_next_action` asserts that the actions differ and that an equal pair fails with `SCENARIO_ACTION_UNCHANGED`. |
| `ARBORA-ACCEPTANCE-R006.1.2` | **P1 decision provenance: the run trace records the action and the claim that caused it.** Behaviour: the trace of run A records the chosen action by name and cites the claim ID whose injection caused it. The cited ID must be one of the retrieved claim IDs of `R006.1` step 4. The trace of the control runs of `R006.1.1` cites no claim for their action. The decision record is the medulla decision log entry that the chosen action commits (`MEDULLA-DECISION-ENGINE-R019`, served `DecisionLog`). Its inputs digest covers the cited claim ID, so a reader can replay the choice. Caller chain: the test client → `meristem.graph.execute_graph` → trace event of the vocabulary `MEDULLA-ORCH-VOCAB-R009` (`action_chosen`, cited claim IDs) → served `DecisionLog` read at the arbora boundary. Meristem applies the received run plan and holds no store (`MERISTEM-BOUNDARY-R043.1`). Shape: trace event `{ run_id, action, cited_claim_ids[], decision_record_id }`. Refusal codes: `SCENARIO_ACTION_UNCITED` when the action has no cited claim or the cited ID was not retrieved, `DECISION_RECORD_MISSING` when the decision record does not resolve. Depends on: `ARBORA-ACCEPTANCE-R006.1.1`, `MEDULLA-ORCH-VOCAB-R009`, `MEDULLA-DECISION-ENGINE-R019`, `MERISTEM-BOUNDARY-R043.1`. | Test: `tests/scenarios/test_p1_closed_loop.py::test_trace_records_action_and_cites_claim` asserts the cited ID, the resolved decision record and both refusal codes. |
| `ARBORA-ACCEPTANCE-R006.1.3` | **P1 is the gate: no later phase is delivered before P1 is VERIFIED.** Behaviour: no row of phases P2 to P5 may be marked delivered (`PIPE-RELEASE-R022`) until `ARBORA-ACCEPTANCE-R006.1`, `.1.1` and `.1.2` are VERIFIED and the latest P1 `ScenarioRun` passed. The check runs in two places. First, the scenario fixture of `R006.2`, `R006.3`, `R006.4` and `R006.7` reads the status of the three rows and the latest P1 run before it starts, and refuses to run otherwise. Second, the release workflow refuses to cut the bundle of any phase after P1 under the same condition (`PIPE-RELEASE-R020` stops with `BUNDLE_NOT_DELIVERED`; the P1 bundle is `releases/P1.yml` of `PIPE-RELEASE-R021`). Caller chain: the nightly job and the pull-request job → `scenario_stack` fixture (`ARBORA-ACCEPTANCE-R006.5`) → phase prerequisite check → the scenario; the release workflow → `scripts/release_scope.py --check`. Shape: refusal body `{ code, phase, open_rows[] }`. Refusal codes: `PHASE_PREREQUISITE_UNVERIFIED` (names the open P1 rows), reusing `BUNDLE_NOT_DELIVERED` on the release side. Depends on: `ARBORA-ACCEPTANCE-R006.1.2`, `PIPE-RELEASE-R020`, `PIPE-RELEASE-R021`, `PIPE-RELEASE-R022`. | Test: `tests/scenarios/test_phase_gate.py::test_later_phase_scenario_refuses_until_p1_verified` asserts the refusal while a P1 row is open and the run once all three are VERIFIED. |
| `ARBORA-ACCEPTANCE-R006.2` | **P2 scenario: the loop is reliable and inspectable.** Steps: 1. One fixture connector ingests 100 records through the SDK runner (`SCION-SOURCE-INGEST-R001`). They land as typed claims with provenance. 2. A query filters claims by source, confidence and valid time. 3. Two writers update one claim at the same version. The second write refuses with `WRITE_CONFLICT` (`MEDULLA-DURABLE-KERNEL-R084`). 4. A fixed suite of 20 tasks runs twice, once without and once with retrieval. Each outcome is recorded as an evidenced claim (`MEDULLA-DECISION-ENGINE-R100`, `MEDULLA-DECISION-ENGINE-R813`). Pass: every claim shows full lineage. No write is lost. The run with retrieval succeeds on at least 2 more tasks than the run without it. A smaller lift fails the scenario with `NO_MEMORY_LIFT`. | Test: `tests/scenarios/test_p2_reliable_loop.py::test_lineage_conflict_and_memory_lift`. |
| `ARBORA-ACCEPTANCE-R006.3` | **P3 scenario: boundaries hold with several agents.** Steps: 1. The meristem boundary gate (`MERISTEM-BOUNDARY-R038`) passes: meristem holds no durable store. 2. Two agents, one human and one A2A peer (`ARBORA-A2A-R001`) write to the same tenant graph under one policy. 3. Node-level visibility (`MEDULLA-IDENTITY-R610`) hides a restricted subgraph from one principal before any query surface. 4. Two agents assert contradicting claims. The write path records a contradiction (`MEDULLA-DECISION-ENGINE-R652`) and keeps both claims. Pass: every write carries provenance, the restricted principal sees zero restricted nodes, and the contradiction record names both claims. | Test: `tests/scenarios/test_p3_multi_agent_boundaries.py::test_shared_state_under_policy_with_contradiction`. |
| `ARBORA-ACCEPTANCE-R006.4` | **P4 scenario: the cross-modal bet and memory maintenance.** Steps: 1. One served query joins a graph neighbourhood, a vector match and an attribute filter in one plan, under one transaction and one security context (`MEDULLA-FEDERATED-QUERY-R720`). The falsification gate (`MEDULLA-FEDERATED-QUERY-R730`) must pass on that plan. 2. A write that breaks a shape refuses at commit (`MEDULLA-TYPED-PACKS-R105`). A small entailment set becomes visible to the next read. 3. Decay and consolidation (`MEDULLA-DECISION-ENGINE-R651`) run, and the agent observes the changed ranking. Pass: the result carries provenance, the gate verdict is recorded, and maintenance never breaks durability or policy. | Test: `tests/scenarios/test_p4_cross_modal_and_maintenance.py::test_one_plan_validation_and_decay`. |
| `ARBORA-ACCEPTANCE-R006.5` | **Scenarios run in process on every pull request.** `arbora/testing/scenario_stack.py` provides the `scenario_stack` fixture. It builds the served arbora application in process, starts a loopback medulla server on a temporary store and runs meristem in process. Each scenario call goes over real HTTP and MCP to that application, so the test exercises arbora's public boundary. Scenarios `.1` to `.4` must finish within 5 minutes in pull-request CI. Scenario `.7` needs connectors and runs only on the stack of `.6`. A scenario that needs a component the stack lacks fails with `SCENARIO_STACK_INCOMPLETE`; it never skips. Caller chain: the pull-request CI job → pytest → the `scenario_stack` fixture → the served arbora application over real HTTP and MCP → the in-process loopback medulla server and meristem run. Shape: new module `arbora/testing/scenario_stack.py` holds the `scenario_stack` fixture and the refusal code `SCENARIO_STACK_INCOMPLETE`. It reuses the host application factory of `ARBORA-HOST` and adds no second server path. | Test: `tests/scenarios/test_scenario_stack.py::test_stack_serves_mcp_and_http_over_one_engine`. |
| `ARBORA-ACCEPTANCE-R006.6` | **An ephemeral deployed stack validates the scenarios nightly.** `deploy/ephemeral/compose.yaml` starts the medulla server and arbora from the commit's built wheels with a fresh store. It also starts the fixture connectors of `ARBORA-ACCEPTANCE-R006.7`. It reaches ready within 120 s. The nightly job (`PIPE-RELEASE-R020`) runs scenarios `.1` to `.4` and `.7` against it over the network, records each result, and removes the stack. The stack uses the same images as production. Only its store and its credentials are disposable. | Test: `tests/scenarios/test_ephemeral_stack.py::test_compose_stack_ready_within_budget` runs in the nightly job. |
| `ARBORA-ACCEPTANCE-R006.7` | **P5 scenario: answers across connectors and across virtual graphs.** The scenario runs only on the ephemeral stack of `ARBORA-ACCEPTANCE-R006.6`. That stack starts three fixture connectors that onboard through arbora. Two of them serve virtual graphs. Every step goes through the served `ask` and `find` operations. Steps: 1. A cross-connector competency question joins facts from at least two connectors' virtual graphs. The supply-chain case takes the supplier from one source and the component and vulnerability from another (`MEDULLA-CQ-XSRC-R002`, `MEDULLA-CQ-XSRC-R012.1`). Each fact names its source, its mapping and its read time. 2. One read-only federated query spans two virtual-graph connectors and the engine-resident facts. The answer cites each source. The engine applies the caller's access rights per source (`MEDULLA-CQ-CONN-R090`). 3. The question the execution question is answered from the tools and skills that the connectors onboarded. The answer names the exact operations in order (`MEDULLA-CQ-ORCH-R012`). 4. A caller who cannot read one source repeats steps 1 and 2. The answer excludes that source and names it in its coverage block with a stable reason code. It never drops the source silently (`MEDULLA-CQ-XSRC-R012.2`). Pass: every fact carries provenance, no answer holds a fact from an unreadable source, and the coverage block lists each excluded source. The `ScenarioRun` record (`MEDULLA-SDLC-R013`) holds the verdict. Phase gate: P4 must have passed. Release `P5` completes when this scenario passes on `main` (`PIPE-RELEASE-R023`). Depends on: `ARBORA-FLEET-R052.1`, `ARBORA-FLEET-R052.2`, `ARBORA-FLEET-R052.4.2`, `MEDULLA-CQ-XSRC-R012`, `MEDULLA-CQ-CONN-R090`, `MEDULLA-CQ-ORCH-R012`, `MEDULLA-SRC-AUTH-R006.1`. | Test: `tests/scenarios/test_p5_cross_source.py::test_answers_join_connectors_and_virtual_graphs_with_coverage` runs in the nightly job against the ephemeral stack. |
| `ARBORA-ACCEPTANCE-R006.8` | **Final program scenario: vision questions are answered through the web UI and a messaging channel.** The scenario runs on the ephemeral stack of `ARBORA-ACCEPTANCE-R006.6` after `ARBORA-ACCEPTANCE-R006.7` passes. A fixed set of vision questions goes to the served `ask` operation through the browser chat route and through one supervised messaging channel. Both channels must return the same answer with the same citations and coverage block. The browser route is `OVERSTORY-API-R011.2`. The channel is supervised by `ARBORA-MESSAGING-R002`. The `ScenarioRun` record (`MEDULLA-SDLC-R013`) holds the verdict. Release `P5` completes only when this scenario passes on `main` (`PIPE-RELEASE-R023`). Depends on: `ARBORA-ACCEPTANCE-R006.7`, `ARBORA-MESSAGING-R002`, `OVERSTORY-API-R011.2`. | Test: `tests/scenarios/test_p5_vision_questions.py::test_web_and_messaging_return_the_same_cited_answer` runs in the nightly job against the ephemeral stack. |
