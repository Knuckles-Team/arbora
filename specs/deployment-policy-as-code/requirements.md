# ARBORA-DEPLOY-POLICY requirements

| ID | Requirement | Verification |
|---|---|---|
| `ARBORA-DEPLOY-POLICY-R001` | **Declarative deployment manifest and plan preview.** Stage: deployment plan. Caller: registered op `deploy.manifest.plan` (effect read, scope `ops:read`) → `arbora/api/ops/deploy.py::handle_manifest_plan` → `arbora/deployment/manifest.py::plan_manifest`. Model `DeploymentManifest` in `manifest.py`: `schema_version`, `name`, `components[]`. A component has `id`, `kind`, `image`, `revision`, `identity_mode`, `secrets_ref` and `capacity{cpu_millis, memory_bytes, replicas}`. `kind` is `engine_shard`, `gateway`, `connector` or `webui`. `image` is a digest reference. `identity_mode` is `none`, `local` or `external`. `secrets_ref` is an `openbao://` or `env://` reference. The op reads the manifest by name from `~/.config/arbora/deploy/manifests/<name>.yaml`; the name matches `^[a-z0-9][a-z0-9_-]{0,63}$`. Parsing uses the strict loader of `arbora/deployment/image_digests.py`: unknown and duplicate keys are errors. Live state comes from the port `LiveStateReader`, backed by one read `fleet.call` named by `~/.config/arbora/deploy.yaml` key `tools.live_state.<target>`. `plan_manifest` returns `DeploymentDiff` entries `{component_id, change, from, to}`, sorted by id. Changes: `create`, `update`, `scale`, `destroy`. Refusals: `MANIFEST_INVALID`, `IMAGE_NOT_DIGEST_PINNED`, `LIVE_STATE_UNAVAILABLE`, `LIVE_STATE_TOOL_NOT_READ`. Writes: none. Depends on: ARBORA-DEPLOY-R017.18, ARBORA-DEPLOY-R017.19. Caller chain: MCP or HTTP `deploy.manifest.plan` → the op registry built by `arbora/api/ops/registry_factory.py` (which lists `policy`, `messaging` and the other op modules) → `handle_manifest_plan` (new, `arbora/api/ops/deploy.py`) → `plan_manifest` (new, `arbora/deployment/manifest.py`) → `LiveStateReader` → one read `fleet.call` (`arbora/fleet/multiplexer_ops.py:256`). Shape: new modules `arbora/api/ops/deploy.py` and `arbora/deployment/manifest.py`; model `DeploymentManifest` and `DeploymentDiff`; follow the module shape of `arbora/api/ops/policy.py` (`operations()` returns `OpSpec` values, handler path `arbora.api.ops.deploy.handle_manifest_plan`); the strict loader reuses `StrictLoader` of `scripts/check_deployment_image_digests.py`, moved to `arbora/deployment/image_digests.py` so the script and the op share one loader. | Test: `tests/api/test_deploy_manifest_served.py::test_plan_returns_typed_diff_and_makes_no_write_call` (L3, `invoke`). `tests/deployment/test_manifest.py::test_unknown_key_duplicate_key_and_floating_image_are_rejected` (L2). |
| `ARBORA-DEPLOY-POLICY-R002` | **Idempotent apply convergence.** Stage: deployment apply. Caller: registered op `deploy.manifest.apply` (effect admin, `confirm=PLAN`, scope `fleet:control`, idempotency `KEY_REQUIRED`) → `handle_manifest_apply` → `arbora/deployment/manifest.py::apply_manifest`. The function recomputes the diff and requires its digest to equal the confirmed `plan_digest`. For each `create` or `update` entry it asks placement (`ARBORA-DEPLOY-R017.1`, `R017.2`) and runs the confirmed steps (ARBORA-DEPLOY-R017.21). The receipt `ApplyReceipt{manifest_digest, components[{id, revision, outcome}], receipt_digest}` carries no timestamp. `receipt_digest` is the SHA-256 of the canonical JSON. A re-run on a converged state has an empty diff, makes zero calls and returns the same receipt. A missing input refuses `MANIFEST_INPUT_MISSING` naming the gap, before any call. Arbora fabricates no input. Writes: governed `fleet.call` effects keyed `deploy:<manifest_digest>:<component>:<node>`. Depends on: `ARBORA-DEPLOY-POLICY-R001`, ARBORA-DEPLOY-R017.21. Caller chain: MCP or HTTP `deploy.manifest.apply` → the op registry → `handle_manifest_apply` (new, `arbora/api/ops/deploy.py`) → `apply_manifest` (new, `arbora/deployment/manifest.py`) → placement and confirmed steps of `ARBORA-DEPLOY-R017.1`, `R017.2` and `R017.21` → governed `fleet.call`. Shape: `ApplyReceipt` frozen dataclass in `arbora/deployment/manifest.py`; `receipt_digest` is SHA-256 over canonical JSON (sorted keys, no timestamp); the idempotency key format is `deploy:<manifest_digest>:<component>:<node>`; reuse the plan recomputation of `plan_manifest` so the confirmed `plan_digest` is checked against a fresh diff. | Test: `tests/api/test_deploy_manifest_served.py::test_second_apply_makes_zero_calls_and_returns_identical_receipt` (L3). `::test_missing_input_names_the_gap_and_creates_nothing` (L3). |
| `ARBORA-DEPLOY-POLICY-R003` | **Drift inspection and destructive-change approval.** Stage: deployment plan and apply. Caller: `deploy.manifest.plan` returns `drift[]` for entries with change `update` or `scale`. It returns `destructive[]` for `destroy`, `scale` below one replica, and any component whose persistent volume is removed. `deploy.manifest.apply` requires the param `approval_elevation_id` when `destructive[]` is not empty. Arbora reads the elevation through the access service (`arbora/access/service.py`). It requires status `approved`, `remaining_ms > 0`, and justification equal to `deploy-destructive:<destructive_digest>`. The two-person rule is the elevation service rule: the approver differs from the requester. Refusals: `APPROVAL_REQUIRED`, `APPROVAL_EXPIRED`, `APPROVAL_MISMATCH`. Drift inspection is read-only. Depends on: `ARBORA-DEPLOY-POLICY-R001`, `ARBORA-DEPLOY-POLICY-R002`, `ARBORA-IDENTITY-R001`. Caller chain: MCP or HTTP `deploy.manifest.plan` and `deploy.manifest.apply` → `handle_manifest_plan` and `handle_manifest_apply` (new, `arbora/api/ops/deploy.py`) → `arbora/security/elevation.py` through `arbora/access/service.py`. Shape: extend `DeploymentDiff` with `drift[]` and `destructive[]`; `destructive_digest` is SHA-256 over the canonical `destructive[]`; the approval check calls the existing `ElevationService` (`arbora/security/elevation.py`) and adds no second approval store. | Test: `tests/api/test_deploy_manifest_served.py::test_manual_replica_change_is_reported_as_drift` (L3). `::test_destructive_apply_needs_a_fresh_approval_and_a_stale_one_expires` (L3). |
| `ARBORA-DEPLOY-POLICY-R004` | **Declarative policy bundles as code.** Stage: policy administration. Caller: registered ops `policy.bundle.validate` (read) and `policy.bundle.bind` (effect admin, `confirm=CONSOLE`, scope `fleet:control`) in `arbora/api/ops/policy.py`. They call the engine methods `ValidatePolicyBundle` and `BindPolicyBundle` (MEDULLA-IDENTITY-R702) through the caller's engine client. Arbora parses the bundle file `~/.config/arbora/policy/<name>.yaml` with the strict loader and sends it unchanged. The engine compiles it into its isolation layer and enforces it in the one access boundary. MCP and HTTP share one decision because both call the same op. Engine refusals `POLICY_SCOPE_BOUND` and `POLICY_SELF_AUTHORIZATION` pass through unchanged. Arbora holds no rule table and no evaluator. Writes: engine only. Depends on: MEDULLA-IDENTITY-R702, `ARBORA-OPS-R009`. Caller chain: MCP or HTTP `policy.bundle.validate` and `policy.bundle.bind` → the op registry built by `arbora/api/ops/registry_factory.py` (which lists `policy`, `messaging` and the other op modules) → `handle_bundle_validate` and `handle_bundle_bind` (new, `arbora/api/ops/policy.py`, next to `handle_policy_read` at line 36) → the caller's engine client → `ValidatePolicyBundle` and `BindPolicyBundle`. Shape: add two `OpSpec` entries to `operations()` in `arbora/api/ops/policy.py` (scopes `policy:read` and `fleet:control`, `confirm=CONSOLE` for bind) and a `PolicyBundle` strict-loader model in new `arbora/deployment/policy_bundle.py`; the bundle goes to the engine unchanged and Arbora keeps no evaluator. | Test: `tests/api/test_policy_bundle_served.py::test_bound_bundle_denies_a_mutation_on_http_and_mcp_with_the_same_decision` (L3, loopback engine). `::test_scope_exclusivity_and_self_authorization_refusals_pass_through` (L3). |
| `ARBORA-DEPLOY-POLICY-R005` | **Epistemic policy predicates.** Stage: policy enforcement. Caller: any registered write op (for example `ingest.submissions.create`) → invoke pipeline → engine mutation → engine access service (MEDULLA-IDENTITY-R703). Arbora adds no predicate code. The pipeline returns the engine refusals `POLICY_EVIDENCE_MISSING`, `POLICY_EVIDENCE_EXPIRED` and `POLICY_CONFIDENCE_LOW` as typed refusals with the engine reason. Missing evidence is never a pass. Depends on: MEDULLA-IDENTITY-R703, `ARBORA-DEPLOY-POLICY-R004`. Caller chain: any registered write op → the invoke pipeline of `arbora/api/ops/` → the engine mutation → the engine access service. Shape: no new module; extend the refusal mapping of the invoke pipeline with the three engine codes `POLICY_EVIDENCE_MISSING`, `POLICY_EVIDENCE_EXPIRED` and `POLICY_CONFIDENCE_LOW` so each returns as a typed refusal carrying the engine reason. | Test: `tests/api/test_policy_epistemic_served.py::test_write_with_valid_evidence_admits_and_expired_or_missing_evidence_refuses` (L3, loopback engine). |
| `ARBORA-DEPLOY-POLICY-R006` | **Served agent surface: llms.txt, best-practice resources, versioned skill export.** Stage: serving. Caller: HTTP `GET /llms.txt` (a `ProtocolRoute` in `arbora/api/http/protocol_routes.py`, owner `arbora.fleet`) → `arbora/fleet/agent_surface.py::build_llms_txt`. The file lists the served operations and docs links of the deployed version and its release digest. MCP best-practice resources register through the FastMCP bridge from the same module. The skill export command `arbora skills export --digest-stamp` writes the skills with the release digest in each header. Every artifact calls `gate_mcp_resource_publication` (`arbora/fleet/mcp_resource_reconciliation.py`) first. A stale or missing receipt refuses `reingestion-unreconciled` and publishes nothing. Depends on: `ARBORA-MCP-RESOURCES-R001`. Caller chain: HTTP `GET /llms.txt` → a new `ProtocolRoute` in the route list of `arbora/api/http/protocol_routes.py` → `build_llms_txt` (new, `arbora/fleet/agent_surface.py`) → `gate_mcp_resource_publication` (`arbora/fleet/mcp_resource_reconciliation.py:75`). Shape: new module `arbora/fleet/agent_surface.py` with `build_llms_txt`, the MCP resource registration and the `--digest-stamp` skill export; each artifact calls the existing gate first and returns its `PublicationGateResult` refusal `reingestion-unreconciled` unchanged. | Test: `tests/fleet/test_agent_surface_served.py::test_llms_txt_and_resources_match_the_deployed_digest` (L3, HTTP and MCP). `::test_stale_or_missing_receipt_refuses_generation` (L3). |
| `ARBORA-DEPLOY-POLICY-R007` | **Rollout records a deployment through deployment.record.** After each successful rollout, the deploy executor must call the served operation `deployment.record`. The call carries the release artifact digest, the target and the time. Caller: the deploy operation entry in the policy-as-code deploy path. A failed record refuses with `UNAVAILABLE` and marks the rollout unrecorded. Depends on: `ARBORA-OPS-R853.1`. Caller chain: MCP or HTTP `deploy.manifest.apply` → `apply_manifest` (new, `arbora/deployment/manifest.py`) → after each successful component rollout → `fleet.call` of the served operation `deployment.record` (`ARBORA-OPS-R853.1`). Shape: one helper `record_rollout(receipt_component)` in `arbora/deployment/manifest.py` that sends the artifact digest, target and UTC time through the same `fleet.call` path as the apply steps; a failed record sets the component outcome to `unrecorded` and refuses `UNAVAILABLE`. | Test: `tests/api/test_deploy_manifest_served.py::test_rollout_records_one_deployment_and_none_on_failure` (planned, see test-spec.md). |
