# ARBORA-DEPLOY-POLICY requirements

| ID | Requirement | Verification |
|---|---|---|
| `ARBORA-DEPLOY-POLICY-R001` | **Declarative deployment manifest and plan preview.** Stage: deployment plan. Caller: registered op `deploy.manifest.plan` (effect read, scope `ops:read`) → `arbora/api/ops/deploy.py::handle_manifest_plan` → `arbora/deployment/manifest.py::plan_manifest`. Model `DeploymentManifest` in `manifest.py`: `schema_version`, `name`, `components[]`. A component has `id`, `kind`, `image`, `revision`, `identity_mode`, `secrets_ref` (optional) and `capacity{cpu_millis, memory_bytes, replicas}`, plus the optional `persistent_volumes[]`. `kind` is `engine_shard`, `gateway`, `connector` or `webui`. `image` is a digest reference. `identity_mode` is `none`, `local` or `external`. `secrets_ref` is an `openbao://` or `env://` reference. The op takes `name` and `target` and reads the manifest by name from `~/.config/arbora/deploy/manifests/<name>.yaml`; the name matches `^[a-z0-9][a-z0-9_-]{0,63}$`. Parsing uses the strict loader of `arbora/deployment/image_digests.py`: unknown and duplicate keys are errors. Live state comes from the port `LiveStateReader`, backed by one read `fleet.call` named by `~/.config/arbora/deploy.yaml` key `tools.live_state.<target>`. `plan_manifest` returns `DeploymentDiff` entries `{component_id, change, from, to}`, sorted by id. Changes: `create`, `update`, `scale`, `destroy`. Refusals: `MANIFEST_INVALID`, `IMAGE_NOT_DIGEST_PINNED`, `LIVE_STATE_UNAVAILABLE`, `LIVE_STATE_TOOL_NOT_READ`. Writes: none. Depends: ARBORA-DEPLOY-R017.18, ARBORA-DEPLOY-R017.19. Caller chain: MCP or HTTP `deploy.manifest.plan` → the op registry built by `arbora/api/ops/registry_factory.py` (which lists `policy`, `messaging` and the other op modules) → `handle_manifest_plan` (new, `arbora/api/ops/deploy.py`) → `plan_manifest` (new, `arbora/deployment/manifest.py`) → `LiveStateReader` → one read `fleet.call` (`arbora/fleet/multiplexer_ops.py:256`). Shape: new modules `arbora/api/ops/deploy.py` and `arbora/deployment/manifest.py`; model `DeploymentManifest` and `DeploymentDiff`; follow the module shape of `arbora/api/ops/policy.py` (`operations()` returns `OpSpec` values, handler path `arbora.api.ops.deploy.handle_manifest_plan`); the strict loader reuses `StrictLoader` of `arbora/deployment/image_digests.py`, the one loader the digest checker (`python -m arbora.deployment.image_digests`) and the op share; the script is gone. | Test: `tests/api/test_deploy_manifest_served.py::test_plan_returns_typed_diff_and_makes_no_write_call` (L3, `invoke`). `tests/deployment/test_manifest.py::test_unknown_key_duplicate_key_and_floating_image_are_rejected` (L2). |
| `ARBORA-DEPLOY-POLICY-R002` | **Idempotent apply convergence.** Stage: deployment apply. Caller: registered op `deploy.manifest.apply` (effect destructive, `confirm=PLAN`, scope `fleet:control`, idempotency `KEY_REQUIRED`; the pipeline refuses an admin effect without console confirmation, and the apply can destroy) → `handle_manifest_apply` → `arbora/deployment/manifest.py::apply_manifest`. The function recomputes the diff and requires its digest to equal the confirmed `plan_digest`. For each `create`, `update` or `scale` entry it assembles the deployment graph for the named target (`ARBORA-DEPLOY-R017.2`) and runs the confirmed steps (ARBORA-DEPLOY-R017.21) under the key prefix `deploy:<manifest_digest>:<component>`. The receipt `ApplyReceipt{manifest_digest, components[{id, revision, outcome}], receipt_digest}` carries no timestamp. `receipt_digest` is the SHA-256 of the canonical JSON. Every manifest component reports outcome `converged`. A re-run on a converged state has an empty diff, makes zero effect calls (the one live-state read still runs) and returns the same receipt. A missing input refuses `MANIFEST_INPUT_MISSING` naming the gap, before any call. Arbora fabricates no input. Writes: governed `fleet.call` effects keyed `deploy:<manifest_digest>:<component>:<node>`. Depends: `ARBORA-DEPLOY-POLICY-R001`, ARBORA-DEPLOY-R017.21. Caller chain: MCP or HTTP `deploy.manifest.apply` → the op registry → `handle_manifest_apply` (new, `arbora/api/ops/deploy.py`) → `apply_manifest` (new, `arbora/deployment/manifest.py`) → placement and confirmed steps of `ARBORA-DEPLOY-R017.1`, `R017.2` and `R017.21` → governed `fleet.call`. Shape: `ApplyReceipt` frozen dataclass in `arbora/deployment/manifest.py`; `receipt_digest` is SHA-256 over canonical JSON (sorted keys, no timestamp); the idempotency key format is `deploy:<manifest_digest>:<component>:<node>`; reuse the plan recomputation of `plan_manifest` so the confirmed `plan_digest` is checked against a fresh diff. | Test: `tests/api/test_deploy_manifest_served.py::test_second_apply_makes_zero_calls_and_returns_identical_receipt` (L3). `::test_missing_input_names_the_gap_and_creates_nothing` (L3). |
| `ARBORA-DEPLOY-POLICY-R003` | **Drift inspection and destructive-change approval.** Stage: deployment plan and apply. Caller: `deploy.manifest.plan` returns `drift[]` for entries with change `update` or `scale`. It returns `destructive[]` for `destroy`, `scale` below one replica, and any component whose persistent volume is removed. `deploy.manifest.apply` requires the param `approval_elevation_id` when `destructive[]` is not empty. Arbora reads the elevation through the access service (`arbora/access/service.py`). It requires an approved elevation (status `active` with `approved_at_ms` set), `remaining_ms > 0`, and justification equal to `deploy-destructive:<destructive_digest>`. The two-person rule is the elevation service rule: the approver differs from the requester. Refusals: `APPROVAL_REQUIRED`, `APPROVAL_EXPIRED`, `APPROVAL_MISMATCH`. Drift inspection is read-only. Depends: `ARBORA-DEPLOY-POLICY-R001`, `ARBORA-DEPLOY-POLICY-R002`, `ARBORA-IDENTITY-R001`. Caller chain: MCP or HTTP `deploy.manifest.plan` and `deploy.manifest.apply` → `handle_manifest_plan` and `handle_manifest_apply` (new, `arbora/api/ops/deploy.py`) → `arbora/security/elevation.py` through `arbora/access/service.py`. Shape: extend `DeploymentDiff` with `drift[]` and `destructive[]`; `destructive_digest` is SHA-256 over the canonical `destructive[]`; the approval check calls the existing `ElevationService` (`arbora/security/elevation.py`) and adds no second approval store. | Test: `tests/api/test_deploy_manifest_served.py::test_manual_replica_change_is_reported_as_drift` (L3). `::test_destructive_apply_needs_a_fresh_approval_and_a_stale_one_expires` (L3). |
| `ARBORA-DEPLOY-POLICY-R004` | **Declarative policy bundles as code.** Stage: policy administration. Caller: registered ops `policy.bundle.validate` (read) and `policy.bundle.bind` (effect admin, `confirm=CONSOLE`, scope `fleet:control`) in `arbora/api/ops/policy.py`. They send the engine identity policy family (`Identity` with `family: policy`, op `validate` or `bind`, MEDULLA-IDENTITY-R702; the family has no separately named methods) through the caller's engine client. Until the pinned engine declares `IdentityOpPolicy` both refuse `UNAVAILABLE` naming it (PIN-LAG guard `arbora/pin_lag/medulla.py`). Arbora parses the bundle file `~/.config/arbora/policy/<name>.yaml` with the strict loader and sends it unchanged. The engine compiles it and enforces it in its one access boundary; enforcement is the engine's and is proven there. MCP and HTTP share one decision because both call the same op. Engine refusals `POLICY_SCOPE_BOUND` and `POLICY_SELF_AUTHORIZATION` pass through unchanged. Arbora holds no rule table and no evaluator. Writes: engine only. Depends: MEDULLA-IDENTITY-R702, `ARBORA-OPS-R009`. Caller chain: MCP or HTTP `policy.bundle.validate` and `policy.bundle.bind` → the op registry built by `arbora/api/ops/registry_factory.py` (which lists `policy`, `messaging` and the other op modules) → `handle_bundle_validate` and `handle_bundle_bind` (new, `arbora/api/ops/policy.py`, next to `handle_policy_read` at line 36) → the caller's engine client → the engine `Identity` policy family. Shape: add two `OpSpec` entries to `operations()` in `arbora/api/ops/policy.py` (scopes `policy:read` and `fleet:control`, `confirm=CONSOLE` for bind) and a `PolicyBundle` strict-loader model in new `arbora/deployment/policy_bundle.py`; the bundle goes to the engine unchanged and Arbora keeps no evaluator. | Test: `tests/api/test_policy_bundle_served.py::test_bundle_ops_send_the_file_unchanged_and_decide_the_same_on_http_and_mcp` (L3). `::test_engine_without_the_policy_family_refuses_unavailable_naming_it` (L3). `::test_scope_exclusivity_and_self_authorization_refusals_pass_through` (L3). |

| `ARBORA-DEPLOY-POLICY-R006` | **Served agent surface: llms.txt, best-practice resources, versioned skill export.** Stage: serving. Depends: `ARBORA-MCP-RESOURCES-R001`. Caller chain: HTTP `GET /llms.txt` → a new `ProtocolRoute` in the route list of `arbora/api/http/protocol_routes.py` → `build_llms_txt` (new, `arbora/fleet/agent_surface.py`) → `gate_mcp_resource_publication` (`arbora/fleet/mcp_resource_reconciliation.py:75`). Shape: new module `arbora/fleet/agent_surface.py` with `build_llms_txt`, the MCP resource registration and the `--digest-stamp` skill export; each artifact calls the existing gate first and returns its `PublicationGateResult` refusal `reingestion-unreconciled` unchanged. | Test: `tests/fleet/test_agent_surface_served.py::test_llms_txt_and_resources_match_the_deployed_digest` (L3, HTTP and MCP). `::test_stale_or_missing_receipt_refuses_generation` (L3). |
